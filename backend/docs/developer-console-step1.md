# Пульт розробника: етап 1

Окремий маршрут `/developer` додає вхід і перевірку технічного сеансу.
Цей етап не переносить Syrve і не додає управління рестораном чи базою.
Наявні пульти, правила ролей персоналу та перемикач `/__dev/roles` збережені.
Змін схеми та міграцій немає. Вхід і перевірка сеансу не звертаються до Neon,
Syrve чи Telegram. Пульт не запускає polling.

HTML не підключає Telegram SDK глобально. Початковий шлях фіксується один раз
перед завантаженням додаткових скриптів: `/developer` і `/developer/` запускають
пульт без SDK. На інших шляхах SDK з тим самим URL завантажується до імпорту
застосунку, щоб наявний Telegram startup уже бачив `window.Telegram.WebApp`.
Помилка завантаження SDK дозволяє запустити звичайний застосунок, як раніше.
Гостьовий екран технічних робіт з датою відновлення 18.10.2026 з поточного
`main` збережений без змін: він залишається в `App` і не перекриває окремий
маршрут розробника.
Якщо окремий модуль пульта не завантажився або його UI завершився помилкою,
локальний error boundary показує повідомлення та кнопку оновлення сторінки.
Технічні деталі помилки не виводяться; повне оновлення запускає вхід заново.

## Налаштування доступу

Доступ закритий за замовчуванням. Параметри задаються на сервері як секрети;
їх не можна записувати в git, frontend, VITE-параметри чи опис PR:

- `DEVELOPER_ACCESS_ENABLED=true` — явне ввімкнення.
- `DEVELOPER_LOGIN` — окремий логін: 3–64 ASCII символи, літери/цифри/`._-`.
  Логін нечутливий до регістру.
- `DEVELOPER_PASSWORD_HASH` — bcrypt hash з cost 12–14. Plaintext пароль
  у конфігурації не підтримується. Створювати hash через `bcryptjs` у приватному
  локальному процесі; не передавати пароль як аргумент shell/CLI чи через журнал.
  Пароль повинен мати щонайменше 16 символів і не більше 72 UTF-8 байтів.
  Рекомендований окремий випадковий пароль з менеджера паролів, cost 12.

Для activation використовується вже наявний `JWT_SECRET`; новий обов'язковий
секрет при запуску не з'являється. Неповна чи некоректна конфігурація закриває
лише вхід розробника. Облікові дані Директора та PIN працівників не підходять.
Перевірити HTTPS і відкриття `/developer` через існуючий SPA fallback перед
активацією на production. Зміна серверних параметрів потребує застосування
нового environment у штатному процесі deployment; цей PR її не виконує.

## Межі безпеки

- JWT діє 15 хвилин, має окремий audience/issuer і ключ, отриманий через
  HMAC від існуючого серверного JWT secret та окремої конфігурації доступу.
  Ключі й хеші не передаються у JWT або відповідях.
- Наявний staff JWT з приписаною роллю `developer` не приймається. Developer
  JWT не перетворюється на staff identity і не має доступу до наявних
  `@Roles('owner')` або інших дій персоналу.
- Зміна логіна, bcrypt hash або JWT root secret скасовує старі сеанси.
  `DEVELOPER_ACCESS_ENABLED=false` закриває вхід і перевірку вже виданих JWT.
- Директор не може створити developer через наявні Staff DTO/API.
- Токен зберігається лише в React state вкладки, окремо від staff storage.
  Reload та локальний вихід прибирають його з UI; копія JWT, збережена поза
  вкладкою, діє до expiry або зміни/вимкнення конфігурації. Server logout-list
  та refresh tokens у цьому етапі відсутні.
- Публічний лише `POST /api/developer/login`; `GET /api/developer/session`
  проходить реальні загальні JWT та role guards. Відповіді мають `no-store`.
- До bcrypt резервуються спроби: до 5 на адресу за 15 хвилин і до 20 загалом
  за хвилину, не більше 200 адрес у пам'яті. Усі спроби, включно з успішними,
  рахуються. Адреса береться з Express request/socket, без самостійного довір'я
  до `X-Forwarded-For`. За reverse proxy адреса може бути спільною.
- Throttle локальний для процесу й очищується після restart. Цей етап
  призначений для поточного одного instance. Перед горизонтальним scaling
  потрібне спільне rate-limit сховище або обмеження на ingress; налаштування
  proxy/сервера цим PR не змінюється.

## Наступний етап

Після окремої перевірки доступу — перенести існуючий Syrve dock та його
серверні права у developer console. Не змінювати POS synchronization,
квоти, правила столів або 15-секундний polling при самому переносі.
Журнал помилок і діагностичний export — наступні незалежні доповнення.
