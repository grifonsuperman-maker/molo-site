# Guest Push — one-time TypeORM apply on the Neon TEST branch only

**Do not run this procedure before its PR has fresh green CI and a reviewed Codex response, is manually merged by the owner, and the owner separately approves the actual test execution.** This is a test of the already-reviewed migration, **not** permission to change production, Render, application business logic or `synchronize`. The previously merged `Guest Push test-branch preflight (check only)` remains read-only and unchanged.

## What the new workflow does

`Guest Push TEST migration (apply test only)` runs only on a manual dispatch of `main` in `grifonsuperman-maker/molo-site`, requires the exact input `apply-guest-push-subscriptions-to-test-push-migration`, builds the backend without database credentials, repeats the existing **read-only** preflight with `MOLO_TEST_PUSH_DB_URL`, then passes a *different*, dedicated TEST-only secret to `guest-push-test-apply.mjs`. The wrapper refuses `production`, `neondb_owner`, `molo_push_preflight_ro`, pooled connections, non-matching hosts, missing SSL, wrong approval or enabled synchronization. The existing operator then takes a transaction, checks eight existing migration rows and the absence of the Push table, executes exactly one TypeORM `up`, verifies migration history and foreign key, and commits. On operator failure its transaction is rolled back. Driver errors and credentials are not printed.

A Neon hostname check does **not prove branch identity**. Confirm the branch, endpoint and role independently in Neon immediately before running. The workflow has no production path, no automatic schedule, no rollback option and **must not use the production owner credential**. An Action with a TEST-only write credential still has the power to change the test copy; limit GitHub write access to trusted maintainers.

## Separate temporary TEST-only writer account (after PR merge; do not reuse the read-only role)

1. In **Neon → MOLO → branch `test-push-migration` → SQL Editor**, confirm this branch is still present, selected, and independently cloned from production. Record the branch's direct (Connection pooling OFF) endpoint hostname privately and confirm it equals the existing GitHub variable `MOLO_TEST_PUSH_EXPECTED_HOST`. Do not expose any connection URLs, passwords or copied booking data. If the branch expired or the eight-row baseline changed, stop: recreate/audit a NEW test branch and recheck the secret and host before doing anything else.
2. With the **test branch's owner SQL Editor only**, create a fresh role `molo_push_migration_runner` with `NOLOGIN PASSWORD NULL`; do **not** create it via Neon's role button if that adds `neon_superuser` membership. After checking that `public.migrations.id` uses the expected sequence (`SELECT pg_get_serial_sequence('public.migrations', 'id');`), grant this TEST-only role only `CONNECT` on `neondb`; `USAGE, CREATE` on schema `public`; `SELECT, INSERT, UPDATE` on `public.migrations`; `USAGE` on the **confirmed** migrations ID sequence; and `REFERENCES (id)` on `public.bookings`. `UPDATE` on the migration journal is needed for the operator's explicit `SHARE ROW EXCLUSIVE` table lock; these test-only privileges can change migration history, so never grant them to the read-only account and never copy the writer role or secret into production. Stop if any grant fails; do not add `neon_superuser`, database `CREATE`, membership in `neondb_owner`, or booking data read/write privileges.
3. While the writer role is still `NOLOGIN`, verify it has **no membership** in `neon_superuser`, `neondb_owner` or other roles; no `CREATEDB`, `CREATEROLE`, `SUPERUSER`, replication or bypass-RLS; no `CREATE` on database `neondb`; and no `SELECT`, `INSERT`, `UPDATE`, `DELETE` or `TRUNCATE` on `public.bookings`. Verify `CREATE` on schema `public`, `REFERENCES` on `bookings.id`, required migration-table privileges and sequence `USAGE`. This is a deliberate, temporary exception for a TEST copy and does not authorize unrestricted production database operations.
4. Only after those checks, give the writer role a **new unique password** and enable LOGIN on the TEST branch. SQL statements containing a password may remain in Neon SQL Editor history: never paste the password or connection URL into chat, a PR, a screenshot, repository code, workflow inputs or logs. Use a password manager. In Neon → TEST branch → Connect, choose `molo_push_migration_runner` and **Connection pooling OFF**. Privately confirm the resulting direct URL contains the exact role, TEST branch hostname and `sslmode=require` or `sslmode=verify-full`. Never use Render's `DB_URL` or the owner connection URL.
5. In **GitHub → molo-site → Settings → Secrets and variables → Actions → Secrets**, create a *separate* repository secret named `MOLO_TEST_PUSH_APPLY_DB_URL` containing only this direct, TEST-only writer connection URL. Keep the existing `MOLO_TEST_PUSH_DB_URL` read-only secret untouched. In **Variables**, `MOLO_TEST_PUSH_EXPECTED_HOST` must contain **only** the independently verified TEST hostname, without a scheme, username, password, port, slash or query parameters. A full connection URL must **never** be stored in Variables.

## Run once, inspect, and revoke

After verifying the test branch exists and the test-only secrets and hostname still point to it, open **GitHub → molo-site → Actions → Guest Push TEST migration (apply test only) → Run workflow → Branch: main**. Enter exactly `apply-guest-push-subscriptions-to-test-push-migration` in `confirmation`; then manually confirm. There is no automatic run on merge. Do not run the read-only `--check` workflow again after a successful apply: it intentionally expects the Push table to be **absent** and will fail after creation.

A green run means the operator reports the ninth migration row, `guest_push_subscriptions` table and its booking foreign key on the TEST copy. It does **not** prove Push delivery, production migration safety, or rollback. Do not issue a second run: the eight-row preflight will fail on a migrated test branch. If the run fails, inspect the **step name and non-secret error only**; do not weaken guards, rewrite migration history, or switch to production credentials. Never paste credentials, connection URLs or booking data in reports.

**Immediately after the test**: delete `MOLO_TEST_PUSH_APPLY_DB_URL` from GitHub repository Secrets; in the TEST branch SQL Editor use `ALTER ROLE molo_push_migration_runner NOLOGIN PASSWORD NULL;` and revoke its temporary `CREATE`, migration-table write, sequence `USAGE` and booking `REFERENCES` grants (or drop the role after verifying that no objects depend on it). Remember the new Push table belongs to the migration runner until ownership or test-branch cleanup is separately planned. Do not delete the test branch before recording schema/history results; do not touch production. Keep the read-only secret separate until a future explicit cleanup decision.

**Rollback testing and production deployment require separate, explicitly approved steps.** The TypeORM migration's `down` refuses to drop a non-empty subscription table and requires a transaction. This workflow does not perform `down`, reset production credentials, or send a Push message.
