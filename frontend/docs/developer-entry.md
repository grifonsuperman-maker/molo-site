# Статична сторінка пульта розробника

Production build створює `dist/index.html` для наявного застосунку та окремий
`dist/developer/index.html` для прямого відкриття пульта. Шлях
`/developer/index.html` працює як звичайний файл без SPA fallback.
На хостингу з directory index також доступні `/developer` і `/developer/`;
усі три адреси потрібно перевірити після публікації.

Обидва HTML використовують локальний `bootstrap.ts`. Початковий шлях
фіксується до завантаження додаткових скриптів. Усі три адреси пульта
визначаються як developer entry та не підключають Telegram SDK. На інших
шляхах порядок запуску SDK і застосунку залишається попереднім.
Ресурси посилаються на абсолютні шляхи від кореня сайту, зокрема `/assets/`.

Перед запуском frontend-тестів потрібно виконати build: packaging regression
перевіряє наявність обох production HTML та файлів, на які вони посилаються.
Це виявляє відсутню сторінку й неробочі шляхи ресурсів до публікації.

Після публікації перевірити HTTP 200 для сторінки та її JS/CSS, відкриття
пульта замість гостьового екрану й відсутність запиту Telegram SDK. Окремо
перевірити наявний гостьовий екран, пульти персоналу та `/__dev/roles`
через їхній попередній спосіб входу.

Статична сторінка не підтверджує роботу серверного входу. Перед ввімкненням
доступу backend має успішно запуститися з новою версією та мати доступ
до своєї бази. Налаштування входу описане в
[інструкції етапу 1](../../backend/docs/developer-console-step1.md).
